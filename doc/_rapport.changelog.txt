## 1.0.20260930.163902 — Première version : rapport d'erreurs commun (--report-err)

Motif de la demande :
  Une option --report-err dans chaque programme : un sommaire des erreurs en fin d'exécution, avec le nom et la version du
  programme, le nom du serveur et le contexte, à coller dans la discussion à la place de la sortie complète (économie de jetons).

Détail des modifications :
  - apps/_rapport.py : classement de la sortie d'un programme (nettoyage des couleurs, masquage des mots de passe, échecs,
    avertissements, recommandations HAUTE/MOYENNE, vérifications ignorées, traces d'appels Python) et construction du rapport :
    programme, version, commande, serveur (nom et nom complet, système, noyau, utilisateur, interpréteur, Python), date, durée,
    code de sortie, contexte lu dans la sortie, versions de toute la suite (fichiers absents signalés), limite de 30 éléments par
    catégorie. Sans échec reconnu mais avec un code de sortie non nul : les 12 dernières lignes.
  - lancer(fonction, programme, version, dossier) : pour les programmes Python — copie stdout et stderr au fil de l'eau (terminal
    conservé), capture SystemExit, Ctrl-C (130) et exceptions (trace dans le rapport, code 1), restaure les flux.
  - Ligne de commande (programmes bash) : python3 apps/_rapport.py --programme … --sortie FICHIER ; --version, --changelog, aide en
    français par ordre alphabétique.
  - apps/_rapport.sh : fonction rapport_si_demande — relance le programme SANS --report-err en copiant sa sortie (tee), conserve le
    code de sortie (PIPESTATUS), appelle _rapport.py, supprime le fichier temporaire ; sans effet avec --help, --version,
    --changelog ; composant ou python3 absent : message clair et exécution normale.

Bugs corrigés :
  - Trouvés par les tests avant livraison : une recommandation FAIBLE avalait la suivante ; le détail d'un échec absorbait une
    ligne « ⚠ » ou une trace d'appels qui le suivait.

Garde-fous et cas limites traités :
  - Une ligne étiquetée ([FAIL], [ATTN], ⚠, [SKIP], recommandation) n'est jamais le détail d'une autre ; l'étiquette explicite l'emporte
    sur les expressions génériques (« [ATTN] … Permission denied » est un avertissement). Une ligne comme « Erreurs Odoo : 0 » n'est pas
    une erreur (les expressions génériques s'ancrent au début de la ligne).
  - Limites connues : seuls les messages étiquetés ou reconnus par une expression connue sont classés ; ce que les sous-processus
    écrivent directement sur le terminal (et non par le programme) n'est pas capturé par les programmes Python.

Vérifications effectuées :
  - 20 tests unitaires (classement, masquage, contenu, exécution Python, ligne de commande) et un test d'intégration par programme.

Action requise de ma part (ou « aucune ») :
  Déployer apps/_rapport.py et apps/_rapport.sh avec le reste de nginx-tools.zip (dossier apps/).
