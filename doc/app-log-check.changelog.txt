## 2.10.20261002.214327 — --by-hour: per-account analysis, bursts, modules, volume

Reason for the request:
  Feedback from trying --by-hour: « 24,645 Session expired only for me; I log in on two PCs and the problem happens when I log in
  on the other one; can we have two active sessions? »; 49,732 problems in one week; the table is hard to read. « Every time a program is run, the first line must display the program's version (even with --help). »

Changes:
  - Accounts: the successful logins of the journal (« Login successful for db:… login:… from IP ») associate each address with its identifiers. Two
    addresses of the SAME account are no longer « several clients »: verdict « A SINGLE ACCOUNT (…) out of N addresses (its workstations) ».
  - Bursts: series of events from an address spaced by less than 10 min; a burst is « triggered » if the same account logged in from ANOTHER
    address within the 5 min preceding it. If at least half of them (and 2 bursts) are: « logging in on one workstation seems to invalidate the other's
    session (a single session per account) »; otherwise: « this is not a single session per account ». Examples listed (time, address, offending login).
  - Modules: INSTALLED modules whose name suggests sessions or login (%session%, %login%, %concurrent%, %single%), read-only from
    PostgreSQL (apps/_odoo_db.py): list, « none » or « unreadable ».
  - Volume: « Log: N lines (≈ X MB) over N days; « Session expired » and their requests: ≈ M lines (P %) ».
  - Table: figures glued WITHOUT thousands separator (« 10 510 » next to other cells read as three numbers); the prose keeps the separator.
  - First line of EVERY run, even --help, --changelog or an unknown option: « NAME vVERSION ». --version only displays the version
    (a single line). Printed after the --report-err hook (which reruns the program), hence only once in the report. The old lines
    that repeated « NAME vVERSION » further down are removed or keep only their own information.

Bugs fixed:
  - Misleading verdict: two addresses of the same account (two PCs) were announced « SEVERAL CLIENTS, unrelated to a restart ». Fixed (A SINGLE ACCOUNT).

Safeguards and edge cases:
  - Addresses without a known login in the window are still judged per address; modules: fixed patterns (no input), validated database, 20 s timeout.
  - Correlation: a burst is « triggered » only by an identifier already seen on the address concerned, from another address.
  - apps/ components not concerned (their output is read by other programs); redirectable data output: version on the error output.

Checks performed:
  - 4 tests: one account on two addresses (verdict, bursts 3 out of 3, modules, read-only), without a previous login, modules unreadable or absent,
    table without separator and volume. They fail on 2.9. - Convention test for the ten programs: --help, --changelog, unknown option (first line, only once) and --version (one line); it fails when a header is removed.

Action required from me (or « none »):
  None. Try: « app-log-check.py --by-hour »; if « 3 burst(s) out of 3 » appears, a login on one PC cuts the other: see the list of modules.

## 2.9.20261002.201545 — Report of problems per hour and per day (--by-hour)

Reason for the request:
  « odoo.http: Session expired » displayed 5,667 times in one day; « an option that gives a report of the pages and the number of errors per
  hour and per day, to see at which hours it happens most often ».

Changes:
  - New option --by-hour [--days N (default 7)] [--top N (default 15)]: reads the journal of the last N days with « -o short-iso » (the machine's
    LOCAL time and the PID of each line; the usual reading, « -o cat », only has Odoo's UTC time) and displays:
    [1] an hour (rows) × day (columns) table of all the problems, only for the hours concerned, with total, bar and the
        « hours without problem » as ranges (colors in a terminal); busiest hours and days;
    [2] the PAGES in error: HTTP requests of 400 and above, and « Session expired » attached to the requested page (the next request of the same
        process, a worker handling one request at a time); identifiers and parameters removed to group similar pages;
        total, days and peak hours of each;
    [3] the ERROR, CRITICAL and WARNING messages, grouped (numbers, fingerprints and tokens neutralized), with the mention « harmless » for
        the known noise (concurrent update conflict…);
    [4] « Session expired » (from 20): peak hours, client addresses with their share (label from apps/team-ips.list), number of
        service restarts (systemd « Started … ») and share of the « Session expired » in the hour following a restart, and a VERDICT:
        A SINGLE CLIENT (80% or more from one address: tab left open with an invalid session), or SEVERAL CLIENTS mostly after a
        restart (sessions not kept: data_dir/sessions), or unrelated to a restart (database change, password, cookies).
  - Neither uses nor modifies the remembered position; BigBlueButton (journals in files): clear message, code 2 (nginx-log-audit.sh --stats).

Bugs fixed:
  - No defect fixed in the old behavior. Two defects of the first version of the report, found when rereading the rendering and fixed
    before delivery: the warnings were grouped with their timestamp (hence never), and the Total line was shifted by one column.

Safeguards and edge cases:
  - Streaming read (never the whole journal in memory) with progress on the error output; journalctl absent or failing: message, code 1;
    --days limited to 1..3650; window without any problem: message; table limited to the last 14 days (the Total covers the whole window).
  - A « Session expired » left without a following request is counted as « (unknown page) »; Python 3.8.

Checks performed:
  - 3 tests: table, peaks, pages, messages, attachment to the page, window requested from journalctl, remembered position intact; three diagnostics
    (one client, several after restart, several without restart); team label; window without problem; invalid --days; BigBlueButton.
    All three fail on 2.8.

Action required from me (or « none »):
  None. Try: « app-log-check.py --by-hour » (7 days) on odoo18; « --days 1 » for the single day.

## 1.0.20260922.083916 — First version

Reason for the request:
  Following the discovery of a protocol-level attack against Odoo's gevent port (direct TLS connections
  bypassing nginx entirely, visible only in Odoo's systemd journal, never in the nginx logs),
  request for a way to monitor this journal for other similar attacks and for unhandled Python traces
  (tracebacks).

Changes:
  - New script, in Python (not bash like chk-nginx-logs.sh): splitting multi-line Python traces is
    much more robust with real regular expressions and strings than with an awk/sed pipeline.
  - Reads the journal via "journalctl -u <service> -o cat" (the "cat" mode removes the whole syslog prefix, leaving
    only the message content — simpler and more reliable than re-parsing that prefix oneself).
  - Groups the lines into "entries": an Odoo structured line (with its own timestamp + level) followed by
    every "raw" line that follows (e.g. a complete traceback, or the "[NB blob data]" lines that journald inserts
    for non-UTF8 bytes it cannot display as is) — up to the next structured line.
  - [1] Protocol attacks/anomalies: detects "Invalid HTTP method"/"Invalid http version" (connections that
    do not even reach nginx well formed — often a direct connection to the gevent port, bypassing
    nginx), with the source IP extracted from gevent's own error message.
  - [2] Python traces grouped by final message (the LAST line looking like "ExceptionName: message" in the
    trace, not necessarily the very last line of the text — a chained Odoo QWeb trace often adds
    context (Template/Path/Node) after the exception itself): a recurring bug appears once, with
    its count, rather than drowned in as many identical blocks as occurrences. One complete example per group
    is shown by default; --full-trace shows one for each group (already the case by default in practice, the
    option name mainly covers the behavior if several examples were added later).
  - [3] Other uncategorized ERROR/CRITICAL lines, as a fallback.
  - --init (the whole available history), --last HOURS (time window, never touches the remembered
    position), and incremental by default (position remembered per service in
    ~/.local/state/chk-odoo-logs/<service>.last) — same conventions as chk-nginx-logs.sh.
  - --service NAME: configurable, because PROD/DEV probably have different unit names.

Bugs fixed:
  - BUG FOUND AND FIXED BEFORE DELIVERY: the timestamp format written in the position file
    (datetime.isoformat(), e.g. "2026-09-22T12:41:02+00:00") is NOT documented as accepted by
    "journalctl --since" (which expects the "YYYY-MM-DD HH:MM:SS" format, without "T" or explicit offset, confirmed
    by external research before the fix). Fixed to use strftime("%Y-%m-%d %H:%M:%S") — verified that the
    argument passed to journalctl has the right format after the fix.

Safeguards and edge cases:
  - journalctl not found, timeout (60s), unknown unit or insufficient rights: explicit error messages
    rather than a silent Python crash.
  - An entry without any structured line before it (window cut in the middle of a trace) is
    ignored rather than crashing the grouping.

Checks performed:
  - Test with the real data supplied by the user (2 IPs making direct TLS connections + a
    real 3-level chained Python trace, KeyError -> KeyError -> QWebException): the 4 protocol anomalies and
    the trace correctly grouped with the right final message ("QWebException", not one of the intermediate KeyErrors).
  - --full-trace test: complete trace displayed correctly, with indentation.
  - Test of the complete incremental cycle: --init writes the position, a following normal call does pass this
    position to "journalctl --since" with the right format, --last never touches this position.
  - python3 -m py_compile on the final file.

Action required from me (or « none »):
  Deploy this script next to the other two. Confirm the exact systemd unit name(s) for DEV/LAB if they differ
  from PROD (--service NAME), and check the access rights to journalctl for the user running it
  (root, or member of the system group "systemd-journal").
