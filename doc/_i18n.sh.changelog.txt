## 1.16.20261020.211944 — Personal configuration file ~/.PROGRAM.conf (not .cfg)

Reason:
  « La règle de fichier de config est de lire avant dans /etc/default/programme.conf et si un fichier existe dans ~/.programme.conf ... pas .cfg »
  « tous les programmes ainsi que la doc »

Changes:
  - New config_migrer_ancien CHEMIN.conf (result in CFG_A_LIRE) and _config_signaler: same rule and same messages as apps/_config.py.
  - config_creer_defaut and config_lire: legacy ~/.app-default.cfg and ~/.PROGRAMME.cfg renamed BEFORE creation and reading.
  - _i18n_relancer / _i18n_anonymize_configure: the legacy name still counts (LANGUAGE, ANONYMIZE) on the first run, before the rename.
  - « Configuration : aucun fichier (cherchés : …) » shows ~/.PROGRAMME.conf.

Bugs fixed:
  none.

Safeguards and edge cases:
  - Legacy ~/.NAME.cfg alone: renamed to ~/.NAME.conf (same content, owner and permissions), one notice on stderr (French and English).
  - Both files present: ~/.NAME.conf is read, ~/.NAME.cfg is IGNORED and reported once per run — never merged nor deleted (its settings may differ).
  - Rename impossible (read-only home…): the legacy file is read as is, with a notice — settings never vanish silently.
  - NGINX_TOOLS_CONFIG_MIGRER=0: no rename. One notice per file and per run, even across child programs (NGINX_TOOLS_CONFIG_SIGNALES).

Checks:
  - New tests test_config_commune.AncienNomPersonnel (Python and bash: rename, both files, read-only home as non-root, English notice, common file);
  - test_conventions: no ~/.NAME.cfg in help, templates and documentation; full suite run-all.sh; ShellCheck 0.11.0 on the bash programs.

Action required:
  none — an existing ~/.PROGRAM.cfg is renamed ~/.PROGRAM.conf automatically at the next run. If both files exist, the program says so:
  move the settings of the .cfg into the .conf, then delete the .cfg.

## 1.13.20261017.200717 — A second Ctrl+C during « Interrompre le programme ? » stops the program

  « [3] Pourquoi le script de test veut effacer des fichiers à l'extérieur de son répertoire (ça va effacer les fichiers de langue qui sont utilisés par mes autres programmes). Et le Ctrl+C affiche ^C et ne pose pas de question de confirmation : […] Effacer ce(s) 7 fichier(s) maintenant ? [o/N] ^C / Interrompre le programme ? [o/N] ^C^C^C^C^C^C^C »

Changes:
  - _ctrl_c_demande: the answer is read in a subshell where Ctrl+C has its normal effect (interrupted subshell or end of input = yes); this shell
    ignores Ctrl+C during the question, then puts its trap back.

    pseudo-terminal. A first fix let bash receive the signal during its own trap: « trap_handler: bad signal 2 … Aborting ». Fix: see Changes.

Safeguards and edge cases:
  none.

Checks:
  - test_ctrl_c.test_bash_ctrl_c_pendant_une_question_sans_erreur: Ctrl+C then Ctrl+C (stops, no bash error), Ctrl+C then n (resumes), Ctrl+C then o.

## 1.11.20261016.173838 — run_interruptible and ctrl_c_child: Ctrl+C answered at once, one question between programs

Reason:
  « [1] copyright → Services-Linux Conseils Inc […] [2] app-log-live.py : faire un lien entre un événement spécifique et ses sondages par billets […] [3] odoo-update-module.sh : avant d'arrêter le service Odoo, vérifier s'il y a beaucoup de gens qui visitent le site et attendre jusqu'à 15 min […] s'il y a des erreurs, faire un retour-arrière avec les versions précédentes des modules (faire une sauvegarde des modules) [4] web-monitor.py --list-users --table : nombre de pages lues et écrites et transmission / réception (en Mo) [5] indiquer le nom de la personne à qui on a envoyé un courriel ainsi que le titre […] [5] Le Ctrl+C ne fonctionne pas lorsque le programme est en cours nginx-log-audit.sh v2.37 (lorsqu'appelé par app-log-live.py) […] il faudrait le trapper dans tous les programmes Python ou BASH, avec une confirmation. Cela fait plusieurs fois que je fais cette demande »

Changes:
  - run_interruptible CMD…: the command runs in the background (SIGINT ignored for it) and bash waits with « wait », which the INT trap interrupts:
    the question comes at once; « no » goes back to waiting and returns the command's real code; « yes » stops it (TERM, CTRL_C_PID) then the program.
  - ctrl_c_child CMD…: runs a program that owns the terminal with a do-nothing trap: the child asks, this program does not ask again.
  - _ctrl_c_arret: stops the command of run_interruptible before the cleanup function.
  - Header: « Copyright (C) 2026  Services-Conseils Linux » (was: Rencontres Linux Québec <info@rencontres-linux.quebec>).

Bugs fixed:
  - Symptom: Ctrl+C seemed dead during a long command (bash runs a trap only when the foreground command ends). Fix: run_interruptible.

Safeguards and edge cases:
  - Not for a command that reads the keyboard (it runs in the background); the code of a command that ends during the question is still returned.

Checks:
  - test_ctrl_c: test_bash_run_interruptible_non_puis_oui, test_bash_parent_et_enfant_une_seule_question; ShellCheck.
