## 1.0.20261013.153900 — Odoo cache warm-up after a restart

Reason for the request:
  « After an Odoo restart, is it possible to load several popular URLs to fill the cache? That way our users will never see these delays. [...] Several of us admins work in Odoo, the admin pages of events, surveys, etc. should be loaded. »

Changes:
  - New program odoo-warmup.py (Python, no dependency): waits for Odoo to answer (--wait), loads the public pages (key PAGES) and all the /web/assets/ they request.
  - Administration (keys LOGIN, KEY_FILE = Odoo API key in a 0600 file, DB): JSON-RPC session, /odoo web client and its assets, menus (load_menus), then get_views (list, form, search, kanban) of each model of MODELS, repeated --repeat times in parallel to reach several workers.
  - --systemd-install / --systemd-remove (--service): .d file that starts the program after each start of the unit (ExecStartPost with systemd-run --no-block: Odoo's start is not delayed).
  - Configuration file /etc/default/odoo-warmup.conf then ~/.odoo-warmup.cfg (common rule), created at first start; catalog lang/odoo-warmup.en.po.

Bugs fixed:
  - None (first version).

Safeguards and edge cases:
  - No write in Odoo: reads only (pages, get_views, menus). API key read from a file (never on the command line); warning if the file is readable by others.
  - Assets are shared (database) but some caches are PER process: parallel repetition raises the chance of reaching each worker without guaranteeing it.
  - Odoo not answering within the delay: clear error, code 2; one page failing does not stop the others; exit code 1 if there are failures.

Checks performed:
  - ruff E9,F; test_odoo_warmup (fake Odoo server: pages, assets, login, get_views, refused login, systemd), test_i18n, test_config_defaut, full suite.
