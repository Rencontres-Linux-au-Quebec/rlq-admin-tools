## 2.70.20261019.012211 — --table: every 5th line underlined; « Account created », « IP country » (RDAP / whois) and « VPN » columns

Reason:
  « Dans web-monitor.py --list-users --table, Afin que ce soit plus lisible dans le tableau, souligne les lignes à tous les modulo 5. et rajoute une colonne afin d'indiquer depuis quand un utilisateur a créé son compte. Indique le pays selon whois et peux-tu indiquer si l'utilisateur utilise un VPN ? »

Changes:
  - compact_table: every 5th data line (5, 10, 15…) underlined across the whole width (UNDERLINE_EVERY = 5; 0 = never); new underline() keeps the
    underline through the colored cells (each « ESC[…m » gets « ;4 »); the last line is not underlined (the separator follows). New colors_on(),
    shared by color_code and underline.
  - New field « created » (« Compte créé » / « Account created »): creation date of the Odoo account (res_users.create_date, local time), cyan when
    less than NEW_ACCOUNT_DAYS (7) days; CSV: date and time; --sort created (newest first; synonyms créé, creation, new).
  - New field « ipcountry » (« Pays IP » / « IP ctry », --table-fields ipcountry or ip-country): country of the OWNER of the address block according to
    RDAP, otherwise whois (apps/_reseau.py fournisseur) for the account's addresses — its IP_LOOKUPS_PER_ACCOUNT (5) most used ones, the main one first,
    plus the latest seen; distinct countries « CA,FR »; yellow when the main one differs from the country of the Odoo contact; « ? » owner unknown.
    CSV: every address with its country and owner.
  - New field « vpn » (« VPN »): the most telling kind among the account's addresses — VPN (NordVPN, Mullvad, Proton, Surfshark, ExpressVPN, PIA…),
    Tor, Relay (iCloud Private Relay, Cloudflare WARP, Fastly), Hosting (data center: M247, DataCamp, OVH, Hetzner, DigitalOcean, AWS, Azure…, or a
    name with hosting / datacenter / server / vps) — from the owner's organisation and network name (VPN_OWNERS, vpn_kind); bold yellow for VPN and
    Tor, yellow for relay and hosting; CSV: every flagged address; --sort vpn.
  - ip_owners(): each public address asked ONCE (8 in parallel, 8 s each), then served by the permanent address cache (apps/_cache_ip.py, 90 days);
    NGINX_TOOLS_INTERNET=off: cache only; progress and elapsed time on stderr (terminal or --verbose only). The lookups only run when the table, the
    CSV or the sort needs ipcountry or vpn.
  - --stats: « Countries (main IP address, RDAP/whois) » and « VPN, Tor, relay, hosting » sections when the owners were looked up.
  - Footnotes of the table for the three columns; --sort help; lang/web-monitor.fr.po (French translations); doc/web-monitor.conf.example;
    docs/en|fr/04-web-monitor.md.
  - apps/_odoo_db.py 1.17: user_profiles returns « created ».

Bugs fixed:
  none.

Safeguards and edge cases:
  - Private, loopback and documentation addresses are never sent to RDAP (no owner: « - »).
  - A lookup failure is never cached (retried next run); component apps/_reseau.py missing: one message, the columns show « ? », the table still prints.
  - The VPN column is a GUESS from the owner's name, written as such under the table: a VPN on a network of unknown name is not detected, a company
    or a school may go out through a data center; « Google Fiber » (home access) is not counted as Google hosting.
  - « IP country » is the country of the registry entry, not a geolocation (a multinational access provider may be registered elsewhere).
  - Underline and colors only in a terminal (never in a pipe, a report or with NO_COLOR); the columns never shift (codes added after the padding).
  - Python 3.8 compatible (BigBlueButton server, Ubuntu 20.04).

Checks:

  - --help (options still sorted), --version, --sort with an unknown key, Python 3.8 syntax (ast feature_version).

## 2.65.20261016.114848 — Suspicious logged-in users, account investigation and ban; wide characters aligned

Reason:
  "[0] When registering for an event in Odoo, validate that people wrote a valid e-mail (example: marieb.essai@gmail'com); add a menu option to list the e-mail errors caused by a wrong address, fix the user's contact and resend the e-mail. [1] In app-log-live.py, show what causes the most latency (SATA, not SSD, with ZFS on Proxmox): % used for I/O over several hours, to decide whether SSD are justified. [2] A program to run on the Proxmox server that details what causes performance problems (CPU, MEM, IO, NET) and suggests settings (ZFS…), light on resources. [3] Alignment problem with Chinese characters in web-monitor.py --list-users --table; a new account (Chinese name) may be a hacker: add a section for suspicious activity of a logged-in Odoo user — do not always trust them. [4] List the suspicious users, offer to investigate all the IPs of a user and blacklist them so they cannot log in to Odoo any more: --ban-odoo-user and --unban-odoo-user, but investigate more before banning (search the e-mail on the Internet, etc.)."

Changes:
  - Summary: new section SUSPICIOUS ACTIVITY OF LOGGED-IN USERS (show_suspects, suspects_list, suspicion): a score per account from signs that each
    have an innocent explanation, so only their sum matters — malicious URLs (+3), burst of pages (+2: BURST_PAGES distinct pages within BURST_WINDOW_S
    seconds), scripting tool User-Agent (+2), Odoo access refused for its UID (+2: "Access Denied by ACLs / record rules" lines), forms submitted in bulk
    (+2: registration, signup, password reset, website form, chatter, survey), address shared by several portal accounts (+2), banned address (+2),
    disposable e-mail (+2), failed logins (+1), password resets (+1), many IP addresses (+1), 4xx rate (+1), new account (+1), e-mail typo (+1).
    2-3 = to watch, 4+ = suspicious; watched accounts always listed. The investigation is offered as a fix at the end of the summary.
  - accumulate_ip / aggregate_ips: form submissions, malicious URLs, tools, User-Agents and the largest burst per address (request_second()).
  - collect_summary: the Odoo journal is also read for "Access Denied by" and "Password reset attempt" (same journalctl call); account databases kept.
  - New options (alphabetical in --help): --ban-odoo-user LOGIN, --internet, --investigate-user LOGIN, --suspect-users, --unban-odoo-user LOGIN,
    --unwatch-odoo-user LOGIN, --watch-odoo-user LOGIN; --yes extended to the ban options.
  - investigate_user: the account in Odoo (apps/_odoo_db.py user_detail: creation, OAuth, logins, registrations, messages, surveys), ALL its IP addresses
    (nginx-log-audit.sh --investigate each, other accounts on them), its activity (account_activity: nginx logs + journal over the whole history), its
    e-mail (apps/_email_check.py: syntax, typo, disposable, DNS MX) and, with consent, the Internet (StopForumSpam, Gravatar, DuckDuckGo); verdict; offer
    to ban or watch.
  - ban_user / unban_user: the Odoo account ARCHIVED (apps/_odoo_db.py set_user_active: no more login, sessions ended, the e-mail stays taken) and the
    addresses used by no other account banned (nginx-log-audit.sh --ban); register apps/_odoo_users.py; --unban-odoo-user restores both.
  - watch_user: register; the account is always listed in the summary and marked [watched] in app-log-live.py.
  - logged_in_ips: logins of BANNED accounts no longer make an address "known user" (otherwise "BANNED IPs THAT LOOK VALID" would offer to unban them).
  - --list-users --table: char_width(), display_width(), truncate_column() count terminal COLUMNS (a Chinese character takes 2): the columns of a line
    with a Chinese name were shifted.
  - lang/web-monitor.fr.po (French of every new message), lang/_email_check.fr.po loaded; doc/web-monitor.conf.example: new options.

Bugs fixed:
  - --list-users --table misaligned. Symptom: the line of « 张三李四 » was 4 columns shorter, every following bar shifted. Diagnosis: the width was
    len() (characters), but East Asian wide characters take two terminal columns. Fix: display_width() (unicodedata.east_asian_width; combining marks 0).

Safeguards and edge cases:
  - No account is ever banned without a person: --suspect-users --yes investigates and bans nothing; --ban-odoo-user asks unless --yes.
  - INTERNAL accounts, the superuser, admin and the public user are never archived (refused in the program AND in the SQL itself).
  - Addresses also used by another account, whitelisted or in a place are never banned with the account; home addresses can be reassigned (said).
  - Internet lookups send the e-mail and the IP addresses to third parties: only on a terminal answer or --internet, never with --yes alone;
    NGINX_TOOLS_INTERNET=off disables them; every network failure gives "unreachable", never a false "clean".
  - A burst counts only pages (assets excluded) and resets when a rotation is read out of order; scores are documented under the section.
  - Register not writable: said, nothing pretended. Python 3.8 compatible.

Checks:
  new test_odoo_users.py (17 tests: section, scores, English, watch, ban and unban with a simulated PostgreSQL and nginx-log-audit.sh, internal account
  refused, Chinese names aligned, register, e-mail checks with simulated DNS and network); test_web_monitor, test_i18n, test_conventions; run-all.sh.

Action required:
  - deploy nginx-tools 1.122 and nginx-tools-tests 1.181 together; run web-monitor.py --summary and read the new section;
  - for the account of the message: sudo web-monitor.py --investigate-user fantome5075@exemple.org (answer y to the Internet search), then decide:

    écrit dans /var/log/surveillance-odoo/ (permissions 640, 30 jours conservés).
  - Anti-rafale élément par élément : chaque alerte est identifiée par des clés stables (vérification en échec, IP
    proposée, type de trace Python — sans compteurs ni heures). Nouveau courriel seulement si une clé NOUVELLE apparaît
    (le courriel indique « NOUVEAU depuis le courriel du … : … ») ou 24 h après le précédent ; un problème qui
    disparaît (résolu) ne déclenche rien.
  - Répertoires d'état SÉPARÉS pour chk-nginx-logs.sh et chk-odoo-logs.py (/var/lib/surveillance-odoo/…) : les
    lancements manuels gardent leurs propres positions de lecture et continuent de montrer les nouveautés.
  - --install-timer [--interval-hours N] : service + timer systemd (fichiers neufs), toutes les N heures à la minute
    5, Persistent=true (rattrape un passage manqué), priorité basse (Nice=10, E/S au repos), SuccessExitStatus=1 (une
    alerte n'est pas une panne du service). --uninstall-timer, --status, --dry-run (aucun courriel, aucune position
    de lecture modifiée), -v/--verbose.
  - Codes de sortie : 0 rien à signaler, 1 alerte levée, 2 erreur d'utilisation.

Bugs corrigés (trouvés en test, avant livraison) :
  - Identification des alertes par titre : un nouvel échec (certificat TLS) ressemblait à l'ancien (HSTS), car les
    deux portent le titre « sanity-check-odoo.py : vérification(s) en échec » — remplacé par des clés par élément.
  - Un problème résolu déclenchait un courriel pour les problèmes restants, déjà signalés.
  - Deux passages dans la même seconde écrasaient le même rapport (suffixe ajouté).
  - BrokenPipeError (trace Python) quand la sortie était coupée (ex. « | head ») : sortie désormais silencieuse.
  - Messages d'argparse en anglais : francisés (même approche que sanity-check-odoo.py).

Garde-fous et cas limites traités :
  - Chaque outil a un délai maximal (15 min) ; un outil qui échoue ou dépasse le délai devient une alerte, jamais un
    arrêt de la surveillance.
  - Root requis pour --run, --install-timer et --uninstall-timer ; --dry-run et --status sans privilège.
  - --interval-hours validé (1 à 24).

Vérifications effectuées (faux outils imprimant des sorties réelles du projet) :
  - Situation saine : « rien à signaler », code 0, rapport écrit.
  - Cinq vrais problèmes mêlés au bruit habituel : 5 alertes, un seul courriel ; traversée bloquée et « access
    forbidden » ignorés.
  - Même situation relancée : pas de courriel ; problème résolu : pas de courriel ; nouveau problème (TLS) ou
    nouvelle IP à bannir : courriel avec la ligne « NOUVEAU ».
  - Outils lancés avec leurs répertoires d'état séparés ; journal système alimenté ; --dry-run sans effet sur l'état ;
    timer généré (OnCalendar=*-*-* 00/2:05:00 pour 2 h), activé puis retiré ; --status ; validations.
  - python3 -m py_compile sur le fichier final.
