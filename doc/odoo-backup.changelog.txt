## 1.7.20260930.132809 — Plusieurs sauvegardes par jour

Motif de la demande :
  Pouvoir spécifier combien de fois par jour la sauvegarde s'exécute, par exemple à 23:00, 9:00 et 16:00.

Détail des modifications :
  - TIMER_TIME accepte UNE OU PLUSIEURS heures HH:MM (espaces ou virgules) : « TIMER_TIME=09:00 16:00 23:00 ». « 9:00 » devient
    « 09:00 » ; heures triées, sans doublon ; valeur invalide (25:00, 12:60, 9h…) : erreur claire. Une seule heure : comportement
    d'avant.
  - Nouvelle option --times "HH:MM …" (ex. --times "23:00 9:00 16:00") : prioritaire sur les fichiers, comme le veut la règle de
    configuration ; affichée dans « ligne de commande (prioritaire) ».
  - --install-timer : une ligne OnCalendar par heure ; message « N sauvegarde(s) par jour, à … ».
  - Nouvelle clé KEEP_RECENT_DAYS (défaut 2) : TOUTES les sauvegardes des N derniers jours (aujourd'hui compris) sont gardées,
    puis la dernière de chaque jour (KEEP_DAILY), semaine, mois. 0 : comportement d'avant.
  - Seuil d'alerte : écart maximal entre deux sauvegardes consécutives (cyclique) + 2 h — une par jour : 26 h (comme avant) ;
    09:00 16:00 23:00 : 12 h. Utilisé par --status, et écrit (max-age-hours) pour web-monitor.py.
  - --status : heures du timer installé ; avertissement s'il diffère des heures configurées (à réinstaller).
  - Ligne « Options » : heures et rétention détaillée.

Bugs corrigés :
  - Avec plusieurs sauvegardes par jour, la rétention d'avant (la dernière de chaque jour seulement) aurait effacé aussitôt les
    sauvegardes précédentes de la journée : c'est pourquoi KEEP_RECENT_DAYS existe.

Garde-fous et cas limites traités :
  - Les heures sont à ±10 min près (RandomizedDelaySec=10min, inchangé). Une sauvegarde encore en cours quand la suivante démarre :
    la seconde s'arrête (code 75, verrou) — peu probable avec des heures espacées.

Vérifications effectuées :
  - Heures normalisées et refusées ; timer à trois lignes OnCalendar et --times prioritaire sur le fichier ; timer installé
    différent de la configuration ; seuil (26, 12 et 14 h, fichier max-age-hours) ; rétention avec KEEP_RECENT_DAYS=2 (hier en
    entier) et 0 (une par jour) ; entier invalide refusé. ShellCheck 0 ; suite complète.

## 1.1.20260929.180340 — Format d'Odoo (.zip importable par sa page, ou .tar.xz) ; restauration

Motif de la demande :
  Sauvegarder avec le fichier manifest dans un .ZIP, pour pouvoir l'importer par la page d'Odoo ; option pour le
  format .tar.xz ; option de restauration, sur un serveur, d'un fichier .ZIP ou .tar.xz.

Détail des modifications :
  - Format d'Odoo (odoo/service/db.py : dump_db) : dump.sql (pg_dump --no-owner, texte), manifest.json (fonction
    manifest_json : odoo_dump, db_name, version, major_version, version_info, pg_version, modules installés avec leur
    version) et filestore/. Fichier BASE_AAAA-MM-JJ_HHMMSS.zip (défaut : importable tel quel par la page
    /web/database/manager d'Odoo) ou .tar.xz (option --format tar.xz ou FORMAT=tar.xz : même contenu, mieux
    compressé), avec son empreinte .sha256. Fonction archiver : ZIP écrit par Python (zipfile, ZIP64) puis relu en
    entier (CRC) ; tar.xz par tar -J puis listé.
  - Vérifications avant acceptation : marque de fin de pg_dump présente dans dump.sql ; archive relue ; contenu
    minimal (dump.sql, manifest.json). Fichiers de travail dans un dossier .partial-XXXXXX, supprimé en cas d'échec.
  - Nouvelle option --restore FICHIER [--db NOM] (fonction restaurer) : .zip ou .tar.xz ; empreinte SHA-256 vérifiée
    si présente ; archive REFUSÉE si un chemin est absolu ou contient « .. » ; résumé du manifest ; base cible = --db,
    sinon db_name du manifest ; JAMAIS d'écrasement (base existante ou filestore non vide : refus) ; base créée avec
    le propriétaire db_user d'Odoo et dump.sql joué sous ce rôle (SET ROLE), comme une restauration par Odoo ;
    filestore copié dans le dossier des filestores et attribué au compte d'Odoo ; en cas d'échec, base supprimée ;
    rappel de neutraliser une copie de production (odoo-bin neutralize).
  - --test-restore : restauration réelle de la dernière archive dans une base et un filestore temporaires, puis
    suppression.
  - Rétention indépendante PAR FORMAT (zip, tar.xz) sur les fichiers au format du programme.

Bugs corrigés :
  - Trouvé avant livraison : la rétention, commune aux deux formats, supprimait le zip du jour dès qu'une sauvegarde
    tar.xz était faite le même jour (ex. sauvegarde manuelle l'après-midi). Désormais indépendante par format.
  - Trouvé avant livraison : résumé du manifest vide (f-string avec \" refusée par Python antérieur à 3.12).
  - Tailles de moins de 1 Ko affichées sans espace (« 10o »).

  - PostgreSQL simulé : ZIP (ordre et contenu, manifest complet, empreinte, --status, --test-restore) ; tar.xz (même
    contenu) ; restauration .zip et .tar.xz sous un autre nom (propriétaire, SET ROLE, filestore copié, manifest
    affiché) ; refus base existante, filestore non vide, archive piégée ; échec de pg_dump et dump incomplet sans
